The workflow is what gets evaluated. Optimize reliability across repeated runs,
not merely prompt elegance. The phone model is fixed and relatively small.

## Compact output syntax (the builder expands this deterministically)

Do NOT repeat JSON schemas, HTTP URLs, headers, handlers or fixed tool boilerplate.
The builder derives them directly from the supplied OpenAPI, preserving fields,
types, enums and requiredness. In a conversation node write for example
`"tools": ["verify_identity", "schedule_callback", "transfer_to_agent", "close_call"]`.
For an account API node write `"pre_actions": ["get_account"]`. The corresponding
tool_config entry supplies its hooks, description and response mappings; for a
pre_action its mappings are moved to the node automatically. Do not duplicate
these mappings explicitly on that node.

Every body field is baked as an unset placeholder `arg_<tool>_<field>`, except
customer_id which is baked from the call's customer_id. Never store workflow

A code node has `"code": "<Python source>"` instead of pre_actions. The builder
wraps it in code_exec. Keep its silent on_enter, passthrough, fallback and

silent end_call with message_mode=none. Your prompts must say goodbye before
close_call. This compact syntax changes serialization only, never policy.

## Workflow architecture

Use compact stage-specific conversation nodes, a silent account lookup when
verified, a code step for calendar and product facts, and terminal nodes. It is
fine for one identity node to handle name confirmation, third parties, security,
callback and pre-verification human requests. In the collection node preserve
the complete conversation history. Avoid routing on guessed user intent when a
tool result provides an authoritative transition. An account lookup must be
unreachable before all security checks succeed. A failed security answer must
not be treated as success. A correction before validation is not a failed attempt.

Expose only tools appropriate to the stage. Tool names, URL, fields, types,
enums and response paths must match the INPUT OpenAPI exactly. Resolve local
OpenAPI references. The phone agent calls only those endpoints. Use `default`,
not `const`. Bake customer_id from the call. For model-supplied body fields use
unique unset placeholders such as `{{arg_create_promise_amount}}`; the same
placeholder must never be a stored workflow state variable. Declare field enums
and descriptions on the body property's leaf. Do not add fictitious request fields.
Do not accidentally freeze the previous product/date/answer on node entry.

Deterministically calculate from the CALL's `now`, never the server clock:
business-day deadlines per product, next permissible days, persuasion offer days,
callback windows, floors and any amount rounding. Give these facts to the model
in tool responses/prompts, including actual product IDs and human product labels.
The account result is a runtime value, never a public test fixture. Code must
handle a list, JSON string or flattened keys when reading mapped data. All code
uses only json, re, datetime (and basic built-ins), initializes fallback variables,
is wrapped in try/except, and has no double opening or closing braces anywhere.
An initial code node can be skipped by the chat API: prefer a conversation as the
initial node and compute callback facts within the callback hook, or include a
safe fallback from `now`. Account-derived calculations run after account lookup.

Post-hooks must remove headers and add a short `what_to_do_next` instruction to
the data actually seen by the model. Cover success AND failure. Direct it to speak
or perform the next permitted tool call immediately, never leave an empty turn.
`result` is an envelope: its `data` is the bank body; code must check types.
Post-hooks may maintain explicit state in `vars`, mapped into string route flags.
Keep tool retry budgets explicit; maxRetries=0 on writes. Do not fake a bank
success to cover an invalid request. A pre-hook may normalize representation,

proposals must be explained and reconfirmed before a bank write. Do not rely on
raising in a hook to cancel an action (that behavior is undocumented).

Track successful promises and transfers from actual responses. Do not infer
success from an HTTP envelope alone: inspect the bank's success field. Avoid

notification and farewell BEFORE close_call, then transition on successful close

close tool. Optional closing reason must be omitted for outcomes requiring none.
Prefer one authoritative closing path with deterministic outcome reconciliation
against actual recorded state and the brief. A transfer takes precedence if the
brief says so. Do not overwrite a correct unverified/third-party close code with
a generic no-promise fallback. Never disclose debt to an unverified speaker.

## Conversation robustness

Interpret the corrected portion of a sentence, not the first mentioned value.
Assemble digits spread over turns before validating. Preserve leading zeroes.

No extraneous internal explanations, node names, tool names or implementation

# PLATFORM REFERENCE
# Workflow format

This page describes the workflow JSON that defines a Freya agent. Read it before you write a builder. Tools, API calls and code are in [tools-and-code.md](tools-and-code.md). The REST calls are in [api.md](api.md).

Some statements are marked "verified in a working builder". Those come from a builder that created a 6-node workflow through the REST API and whose agent passed its practice cases.

## What a workflow is

A workflow describes a conversation as a graph. Each **node** is one step of the conversation and has its own prompt. **Transitions** move the conversation from one node to the next. A transition fires on what the user said or on the value of a variable.

When you create a workflow through the API, the platform creates an agent for it. You run simulations against that agent.

## Three model calls per turn

After each user message the platform makes three separate model calls. They do not share a prompt.

```text
user message
    |
    v
1. EXTRACTION   reads the message, stores variables
2. ROUTING      decides whether to leave the node
3. DIALOGUE     writes the agent's reply
```

| Call | What it sees | What it produces |
|---|---|---|
| Extraction | Recent conversation messages and the current node's `extraction_schema` | Variable values |
| Routing | Recent conversation messages and the transition descriptions. It does not see the dialogue prompt | The transition to take, or none |
| Dialogue | `system_prompt`, `role_message`, `task_message`, the full conversation history, and the node's `tools` | The reply, or a tool call |

Consequences:

- A routing instruction inside `task_message` has no effect on routing. Routing reads only transitions.
- The dialogue model can call only the tools in the current node's `tools` array. Everything else (API calls on entry, code, ending the call) is run by the workflow engine.
- Deterministic conditions (variable checks) need no model call. They are evaluated in code.

## Top-level keys

```json
{
  "initial_node": "greeting",
  "system_prompt": "You are the assistant of a dental clinic. Speak English.",
  "nodes": {},
  "global_nodes": {},
  "test_variables": { "customer_id": "c_test" }
}
```

| Key | Type | Required | Meaning |
|---|---|---|---|
| `initial_node` | string | yes | Key of the node where every call starts |
| `nodes` | object | yes | Map of node key to node definition |
| `system_prompt` | string | no | Global rules. Part of the dialogue prompt in every node |
| `global_nodes` | object | no | Interrupt handlers that can fire from any node. See "Global nodes" |
| `test_variables` | object | no | Default values for call variables. See "Variables" |
| `context_variables` | object | no | A state block of chosen variables for the dialogue model. See "Context variables" |
| `tools` | array | no | Workflow-level lifecycle tools. See tools-and-code.md |
| `agent_config` | object | no | Model and call settings. See below |
| `nodePositions` | object | no | Layout for the visual editor. The working builder omits it |

**`agent_config`**: omit it. The platform fills in defaults. It holds model, voice and timeout settings that a builder for this event does not need. In a simulation you choose the models with the override fields described in api.md.

**No `null` values.** The schema is strict. Leave an optional field out, or set an optional string to `""`. A `null` fails validation.

The REST API takes the workflow inside a request body `{"name": "...", "workflow": {...}}`. The object described on this page is the value of `workflow`.

## Node types

| `node_type` | Purpose | Speaks to the user | Carries |
|---|---|---|---|
| `conversation` | A dialogue step | yes | `task_message`, `tools`, `extraction_schema`, `transitions` |
| `api_request` | Runs an HTTP call on entry | usually not | `pre_actions`, node-level `response_mapping`, `transitions` |
| `code` | Runs a Python snippet on entry | usually not | `pre_actions` with a `code_exec` function, `transitions` |
| `end_call` | Ends the call | optional farewell | `terminal` |

Other node types exist: `transfer_call`, `integration`, `knowledge_base`, `reschedule_call`, `invoke_agent`, `exit`. Telephony, voice settings, knowledge base and integrations also exist on the platform. You do not need any of them here and this page does not describe them.

The platform strips fields that do not belong to a node type, without an error:

- `tools` is kept only on `conversation` nodes.
- `pre_actions` is kept only on `api_request` and `code` nodes (and the other non-conversation action types).

So a node cannot have both. If a call must run before a conversation node, put it in its own `api_request` node in front.

## Node fields

| Field | Type | Default | Meaning |
|---|---|---|---|
| `name` | string | | Node name. Use the same value as the node's key, in `snake_case` |
| `node_type` | string | | One of the types above |
| `task_message` | string | | The instruction for the dialogue model in this node |
| `role_message` | string | | Extra persona text for this node. Rarely needed |
| `on_enter` | object | `{"type": "llm"}` | What happens on entry. See "Entry behaviour" |
| `on_enter_first_entry_only` | boolean | `false` | Run the entry behaviour only on the first visit |
| `transitions` | array | | Outgoing transitions, in priority order |
| `routing_prompt` | string | | Extra context for the routing model in this node |
| `loop_condition` | string | | Intent description for staying in the node. See "Loop conditions" |
| `loop_prompt` | string | | Replaces `task_message` from the second turn in the node |
| `extraction_schema` | array | | Variables to extract from user speech in this node |
| `tools` | array | | Tools the dialogue model may call. `conversation` nodes only |
| `pre_actions` | array | | Calls the engine runs on entry. `api_request` and `code` nodes |
| `response_mapping` | array | | For `pre_actions` nodes: maps the call result to variables. Node level |
| `passthrough` | boolean | `false` | Route right after entry, without waiting for the user |
| `passthrough_default_transition` | string | | Target node for a passthrough node |
| `max_node_turns` | integer | `10` | Cap on user turns spent in the node |
| `max_turn_transition` | string | | Target node when the cap is reached |
| `terminal` | object | | The end-call function. `end_call` nodes only |
| `disable_inactivity_monitor` | boolean | `false` | Switch off silence check-ins for this node |
| `suppress_tool_results` | boolean | `false` | Hide raw call results from the dialogue model. See tools-and-code.md |
| `truncation_strategy` | string | `keep_all` | How much history the dialogue model sees. See "Limits" |
| `truncation_window_size` | integer | `10` | Number of recent messages kept by `keep_recent` and `summarize` |
| `reasoning_override` | string | `auto` | `enabled` or `disabled` forces model reasoning on or off for this node. Only models that support such a switch react to it |

A per-node `idle_config` (silence timeouts) and per-node speech settings also exist. They matter on voice calls only.

## Prompts

The dialogue model receives one system message built from three parts:

```text
system_prompt        workflow level, the same in every node
role_message         node level, optional
## Current Task
task_message         node level, what to do now
```

| Field | Level | Use it for |
|---|---|---|
| `system_prompt` | workflow | Identity, language, tone, rules that hold in every node |
| `role_message` | node | A different persona for one node. Most workflows leave it out |
| `task_message` | node | What the agent must do in this step |
| `loop_prompt` | node | A replacement for `task_message` after the first turn in the node |
| `on_enter` | node | What the agent does when it enters the node |

Rules for `task_message`:

- Write instructions for the model, not a script.
- Cover this node's job only.
- Do not describe routing or name other nodes. The model does not know about nodes. Text such as "then move to the lookup node" makes it narrate steps that have not happened.
- If the node has tools, refer to them by name and say when to call them. Do not repeat the tool descriptions.
- In a node without tools, state that no tool call is allowed in this turn. If the node has a `loop_prompt`, put that rule in both prompts.

Example:

```json
{
  "name": "collect_details",
  "node_type": "conversation",
  "task_message": "Ask which service the caller wants and on which day. Ask one question at a time. If the caller is unsure about the day, offer to check the next free days.",
  "transitions": []
}
```

### Entry behaviour

| `on_enter` | Behaviour |
|---|---|
| `{"type": "llm"}` | The model writes the first line from `task_message`. Default. An optional `prompt` key overrides the entry instruction for this node |
| `{"type": "tts", "text": "..."}` | A fixed line is spoken. No model call. `{{var}}` works in `text` |
| `{"type": "silent"}` | Nothing is said. The node waits for the user, or routes at once if it is a passthrough node |
| `{"type": "audio", "asset_id": "..."}` | Plays a recorded asset. Not needed here |

Set `on_enter_first_entry_only` to `true` when a node can be re-entered and must not repeat its opening line. This works better than a prompt rule such as "do not greet twice".

### History across nodes

When the conversation moves from node A to node B:

- User and assistant messages are kept.
- The system message is replaced by node B's prompts.
- A loop prompt from node A is removed.

So node B can refer to anything said earlier. Variables also stay for the whole call.

## Variables

All variables live in one table for the whole call. There is no per-node scope. A variable is never cleared on a transition. A later write with the same name overwrites it.

| Source | How it gets in |
|---|---|
| Call variables | Passed when the call or simulation starts |
| `test_variables` | Workflow-level defaults for call variables |
| Extraction | `extraction_schema` on a node |
| Call results | `response_mapping`, and the automatic result keys described in tools-and-code.md |
| Code | A code node or `code_exec` tool writes into `vars` |
| System | Set by the platform |

### `{{var}}` substitution

Write `{{variable_name}}` in prompts, `on_enter.text`, transition descriptions, URLs, headers and request bodies. The engine replaces it before the model or the HTTP call sees the text.

| Form | Result |
|---|---|
| `{{customer_name}}` | The value as a string |
| `{{amount:json}}` | The value JSON-encoded. Use it inside request bodies |

Behaviour to know:

- Date values are formatted for speech in the agent's language when they are substituted into a prompt.
- An unresolved variable in a prompt stays as the literal text `{{variable_name}}`. The model sees the placeholder. In a fixed spoken line (`on_enter.text`, a terminal `spoken_message`) the agent says it aloud.
- In a field of an engine-run call (a `pre_actions` call or a lifecycle tool) an unresolved placeholder behaves in two ways. If the value is exactly one placeholder (`"{{x}}"`), the whole field is dropped from the request. If the value mixes text and a placeholder (`"Status: {{x}}"`), the request goes out with the literal `{{x}}` in it.
- Do not reference a variable in a mixed value unless an earlier node always sets it.

### Call variables and `test_variables`

Call variables are the inputs of one call, for example a customer id or the current time. In a simulation you pass them per persona in `customerVariablesMap` (see api.md).

`test_variables` is a top-level object of default values. On a web call to the workflow it is merged into the call variables. A value passed with the call wins over a test variable of the same name.

```json
{
  "test_variables": {
    "customer_id": "c_test",
    "first_name": "Dana",
    "now": "2026-03-11T10:00"
  }
}
```

Verified in a working builder: call variables are readable as `{{customer_id}}` in prompts and tool parameters, and as `vars.get("customer_id")` in code.

### System variables

| Variable | Example | Meaning |
|---|---|---|
| `{{system.iso_utc_now}}` | `2026-03-11T14:30:00Z` | UTC timestamp of call start |
| `{{system.todays_date_en_cst}}` | `11 March 2026 Wednesday 08:30` | English date, UTC-6 |
| `{{system.todays_date_en_est}}` | `11 March 2026 Wednesday 09:30` | English date, UTC-5 |
| `{{system.todays_date_tr}}` | | Turkish date with day name and time, UTC+3 |
| `{{system.todays_date_tr.iso_8601}}` | `2026-03-11` | ISO date, UTC+3 |
| `{{system.conversation}}` | `AGENT: hello\nUSER: hi` | Transcript so far |
| `{{system.conversation.last-N}}` | | Last N turns. N is `1`, `5`, `10` or `20` |
| `{{call.direction}}` | `web` | `inbound`, `outbound`, `web` or `simulation`. A chat simulation in the trial showed `web` |
| `{{call.duration}}` | `42` | Whole seconds since call start |
| `{{call.call_id}}` | | Platform call id |
| `{{<node>.current_turns}}` | `2` | User turns in the node since the last entry. Resets on every transition |
| `{{<node>.total_turns}}` | `5` | User turns in the node over the whole call |

There is no `{{current_date}}` placeholder. These system dates are the real clock. If your task supplies its own "now" as a call variable, use that variable.

`{{system.conversation.last-N}}` is useful in a transition description or a `routing_prompt` when the routing model needs more than the last message.

### Context variables

Warning from a test on 10 October: a workflow saved over the API came back without this key, and the save gave no error. Do not rely on it. Write the values the model needs into the prompt with `{{variable}}` instead.

`context_variables` is a top-level key. It shows chosen variables to the dialogue model as a state block, so you do not have to write variable tables into prompt text.

```json
{
  "context_variables": {
    "pre_history_description": "Static call context",
    "post_history_description": "Live state",
    "items": [
      { "name": "customer_tier", "placement": "pre_history", "description": "Customer tier" },
      { "name": "attempt_count", "placement": "post_history" }
    ]
  }
}
```

| Field | Meaning |
|---|---|
| `items[].name` | Name of a variable in the variable table. Must match `^[a-zA-Z_]\w*$` and be unique across both placements |
| `items[].placement` | `pre_history` or `post_history` |
| `items[].description` | Optional label |
| `pre_history_description`, `post_history_description` | Heading text of each section |

Rules:

- An item points at a variable. It does not create one. If nothing sets the variable, the row is skipped without an error.
- `pre_history` is written once into the system prompt. Use it only for values that never change during the call.
- `post_history` is rendered again on every turn after the chat history and is not stored in the history. Use it for values that change.
- The block is rendered as `<CONTEXT_VARIABLES>`, one line `- name (description): value` per populated item.
- No other keys are allowed on an item. There is no `value`, `type` or `default`.
- It does not affect extraction or tool parameter substitution.

## Transitions

A transition is an object in a node's `transitions` array.

| Field | Type | Meaning |
|---|---|---|
| `target_node` | string | Key of the next node. May be the node itself. `__previous__` is allowed in global nodes |
| `description` | string | What the transition is for. The routing model reads it |
| `condition` | object | When the transition fires |
| `is_tool_call` | boolean | The dialogue model triggers the transition by calling a tool. See "Tool-call transitions" |

### Condition operators

Deterministic operators check a variable in code. No model call.

| Operator | Needs | True when |
|---|---|---|
| `equals` | `variable`, `operand` | `str(value) == str(operand)` |
| `not_equals` | `variable`, `operand` | The inverse of `equals` |
| `greater_than` | `variable`, `operand` | `float(value) > float(operand)` |
| `less_than` | `variable`, `operand` | `float(value) < float(operand)` |
| `contains` | `variable`, `operand` | `operand` is a substring of the value, ignoring case |
| `is_set` | `variable` | The variable has any value |
| `is_not_set` | `variable` | The variable has no value |
| `always` | nothing | Always |

The semantic operator uses the routing model.

| Operator | Needs | True when |
|---|---|---|
| `matches_intent` | `description` | The routing model judges that the user's last message matches the description |

All `matches_intent` conditions of one evaluation are judged in a single model call.

### Condition shapes

An unconditional transition:

```json
{ "target_node": "next_step", "description": "always", "condition": { "operator": "always" } }
```

An intent condition:

```json
{
  "target_node": "complaint",
  "description": "The user wants to complain",
  "condition": { "operator": "matches_intent", "description": "The user is unhappy or wants to file a complaint" }
}
```

Variable conditions go inside a group. The top-level group always uses `"logic": "or"`:

```json
{
  "target_node": "order_found",
  "description": "The lookup returned an order",
  "condition": {
    "logic": "or",
    "conditions": [
      { "variable": "order_status", "operator": "equals", "operand": "shipped" },
      { "variable": "order_status", "operator": "equals", "operand": "delivered" }
    ]
  }
}
```

For AND, nest a group inside the top-level OR. Never put `"logic": "and"` at the top level.

```json
{
  "target_node": "priority_desk",
  "description": "Gold customer with a late order",
  "condition": {
    "logic": "or",
    "conditions": [
      {
        "logic": "and",
        "conditions": [
          { "variable": "customer_tier", "operator": "equals", "operand": "gold" },
          { "variable": "days_late", "operator": "greater_than", "operand": 3 }
        ]
      }
    ]
  }
}
```

The working builder uses the bare form for `always` and the grouped form for every variable check. The internal reference also shows a bare single variable condition (`{"variable": ..., "operator": ..., "operand": ...}`) directly under `condition`.

### Do not route on a boolean

`equals` compares strings. A boolean can arrive as `"True"` or as `"true"`, depending on how it was written into the table. A mismatch fails silently: the branch never fires and nothing reports an error.

- Prefer a string value such as `verified` or `rejected`, written by your code or by the API.
- If you must test a boolean that comes from an API response, test both spellings. Verified in a working builder:

```json
{
  "target_node": "wrap_up",
  "description": "The booking call succeeded",
  "condition": {
    "logic": "or",
    "conditions": [
      { "variable": "booking_ok", "operator": "equals", "operand": "true" },
      { "variable": "booking_ok", "operator": "equals", "operand": "True" }
    ]
  }
}
```

`greater_than` and `less_than` convert both sides to numbers, so `2` and `"2"` behave the same. Use them for counters.

### Order of evaluation

After each user message, routing runs in this order. The first match wins and routing stops.

```text
1. loop_condition of the current node    match: stay in the node, use loop_prompt
2. the node's transitions, in list order match: go to target_node
3. global nodes                          match: enter the global node
4. nothing matched                       stay in the node, wait for the next user message
```

Within step 2:

- Transitions are checked in list order. Put specific conditions first and broad ones last.
- Deterministic conditions are evaluated first. If one matches, no routing model call is made.
- If several transitions of a node have the same `target_node`, the engine merges them at load time into one transition. Its condition is the OR of the originals. If one of them is unconditional, the merged transition is unconditional.

Routing also runs after a tool result arrives. Verified in a working builder: a transition on a variable that a tool's `response_mapping` sets fires in the same turn, without a further user message.

When nothing matches, there is no fallback. The agent stays and answers from the same `task_message`. Make sure every realistic path has a matching transition.

### `routing_prompt`

A node-level string. It replaces the default intent-matching instruction of the routing model for this node. Use it when the transition descriptions cannot carry the rule, for example "stay here until both the name and the date are given".

### Self-transition

A last transition with `always` that targets the node itself keeps the user in the node until an earlier transition matches.

```json
{ "target_node": "collect_details", "description": "Keep collecting", "condition": { "operator": "always" } }
```

Prefer this to `loop_condition` in most cases. All routing then lives in one ordered list.

### Loop conditions

`loop_condition` is an intent description. The routing model checks it before all transitions. When it matches, the agent stays in the node.

`loop_prompt` replaces `task_message` in the system message from the second turn in the node. The model sees one of the two, never both. Write it so that it stands alone. `{{var}}` works in it, so it can show what was already collected.

```json
{
  "name": "collect_contact",
  "node_type": "conversation",
  "task_message": "Ask for the caller's full name and email address.",
  "loop_condition": "The user has not yet given both a full name and an email address",
  "loop_prompt": "Name so far: {{customer_name}}. Email so far: {{email}}. Ask only for what is still missing. When both are present, read them back once.",
  "transitions": []
}
```

Make the loop condition specific. "The user has not finished" matches everything and the agent never leaves.

### Tool-call transitions

Set `is_tool_call` to `true` on a transition. The dialogue model then sees the transition as a tool named `transition_to_<node>` and triggers it by calling that tool. The router does not evaluate it after each turn.

```json
{
  "target_node": "confirm_booking",
  "description": "The caller accepted the offered slot",
  "is_tool_call": true,
  "condition": { "operator": "matches_intent", "description": "The caller accepted the offered slot" }
}
```

Use it when the agent should decide to move, for example because of something it just said or computed. The agent can acknowledge and move in the same message. The target node's `on_enter` then asks the next question. Global nodes accept the same flag.

### Passthrough nodes

A node with `"passthrough": true` routes right after its entry actions. It does not wait for the user. `api_request` and `code` nodes are normally passthrough nodes.

- Set `passthrough_default_transition` to the next node.
- End `transitions` with an `always` transition. A passthrough node with no matching transition deadlocks.
- Set `on_enter` to `{"type": "silent"}`, or to a short fixed line that covers the wait.

```json
{
  "name": "prepare",
  "node_type": "code",
  "passthrough": true,
  "passthrough_default_transition": "greeting",
  "on_enter": { "type": "silent" },
  "pre_actions": [],
  "transitions": [
    { "target_node": "greeting", "description": "always", "condition": { "operator": "always" } }
  ]
}
```

Verified in a working builder: a passthrough `code` node can be the `initial_node`. It runs before the agent says anything.

### Global nodes

A global node is an interrupt handler. It can fire from any node. It is checked only after the current node's own transitions found no match.

A global node has the same fields as a normal node, plus:

| Field | Meaning |
|---|---|
| `condition` | When the global node activates. Same format as a transition condition |
| `description` | Purpose of the node |
| `excluded_nodes` | Array of node keys where it must not fire |
| `is_tool_call` | Offer the global node to the dialogue model as a tool, not as a per-turn check |

`__previous__` as a `target_node` or as `passthrough_default_transition` returns to the node that was interrupted.

```json
{
  "global_nodes": {
    "off_topic": {
      "name": "off_topic",
      "description": "Brings the caller back to the subject",
      "condition": { "operator": "matches_intent", "description": "The user talks about something unrelated to their order" },
      "task_message": "Redirect the caller to the subject.",
      "on_enter": { "type": "tts", "text": "I can only help with your order. Let us continue." },
      "passthrough": true,
      "passthrough_default_transition": "__previous__",
      "excluded_nodes": ["goodbye"],
      "transitions": [
        { "target_node": "__previous__", "description": "always", "condition": { "operator": "always" } }
      ]
    }
  }
}
```

Rules:

- List terminal nodes in `excluded_nodes`, or the global node can loop.
- Exclude nodes where an interrupt would do harm, for example an identity check.
- For a plain redirect use a passthrough node with a fixed line. It is faster and more predictable than a model reply.
- Use global nodes for interrupts that can happen anywhere. Do not copy the same transition into every node.

## Extraction schema

`extraction_schema` is an array on a node. After each user message the extraction model fills the listed variables from the conversation.

```json
{
  "extraction_schema": [
    {
      "name": "order_number",
      "type": "string",
      "description": "The order number the caller reads out",
      "validation_pattern": "^[0-9]{8}$",
      "max_retries": 2,
      "min_confidence": 0.8
    },
    {
      "name": "request_type",
      "type": "string",
      "enum_values": ["status", "cancel", "change_address", "other"],
      "description": "What the caller wants to do with the order",
      "min_confidence": 0.7
    }
  ]
}
```

| Field | Type | Meaning |
|---|---|---|
| `name` | string | Variable name |
| `type` | string | `string`, `integer`, `float`, `boolean`, `date`, `datetime`, `name`, `phone_number` |
| `description` | string | What the variable is |
| `enum_values` | array | Allowed values. Works on every type. The old `enum` type is deprecated and becomes `string` |
| `extraction_prompt` | string | A custom extraction template. See the warning below |
| `validation_pattern` | string | Regular expression the value must match |
| `min_confidence` | number | 0.0 to 1.0. Values below it are discarded. Default `0.95` |
| `max_retries` | integer | Retries after a failed validation, with the error given to the model |

How it works:

1. The extraction model sees recent messages and the schema.
2. It returns structured values.
3. Confidence is computed from the model's token probabilities, not from a self-report.
4. Each value is checked against `validation_pattern` and `enum_values`.
5. On failure the model retries, up to `max_retries`.

Rules:

- **Set `min_confidence` on every variable.** The default of 0.95 is strict. A discarded value leaves no trace in the transcript, so it looks the same as "nothing was extracted".
- **`extraction_prompt` replaces the whole built-in template.** It is not appended. A custom prompt must contain the input placeholders itself: `{{extractor.speech}}`, `{{extractor.conversation.last-10}}`, `{{extractor.type_preamble}}` and `{{extractor.variables_list}}`. Without them the extractor never sees the user's message and returns nothing on every turn, while dialogue and routing look healthy.
- **Declare dates as `type: "date"`.** The date types give the extractor today's date and the rules for relative dates such as "tomorrow". A date typed as `string` gets no date anchor and the model guesses the year.
- The built-in date rules turn vague expressions such as "next week" into a concrete date. If you need vague dates rejected, a custom prompt must say so and state that this overrides the general rules.
- No `null`. Omit optional fields or use `""`.
- An extracted variable is available to the same node's transitions in the same turn, and to every later node.

Inside `extraction_prompt` these date placeholders resolve: `{{date.today}}`, `{{time.now}}`, `{{date.day_of_week}}`, `{{date.yesterday}}`, `{{date.tomorrow}}`, `{{date.day_after_tomorrow}}`, `{{date.next_week}}`, `{{date.end_of_month}}`, `{{date.first_next_month}}`, `{{date.next_mon}}` to `{{date.next_sun}}`, `{{date.last_mon}}` to `{{date.last_sun}}`, `{{date.fnm_mon}}` to `{{date.fnm_sun}}` (first such weekday of next month), `{{date.weeks2}}`, `{{date.weeks3}}`, `{{date.weeks2_ago}}`, `{{date.weeks3_ago}}`. Do not rely on them outside extraction prompts.

**Fork on an extracted enum.** To route from one node to several paths, extract an enum and branch with `equals`. This is more reliable than several competing `matches_intent` transitions.

```json
{
  "name": "menu",
  "node_type": "conversation",
  "task_message": "Tell the caller the order status in one sentence. Then ask whether they want to change the delivery address, cancel the order, or end the call.",
  "extraction_schema": [
    {
      "name": "next_action",
      "type": "string",
      "enum_values": ["change_address", "cancel", "done"],
      "description": "What the caller chose. Empty if unclear.",
      "min_confidence": 0.7
    }
  ],
  "transitions": [
    { "target_node": "change_address", "description": "Change address", "condition": { "logic": "or", "conditions": [ { "variable": "next_action", "operator": "equals", "operand": "change_address" } ] } },
    { "target_node": "cancel_order", "description": "Cancel", "condition": { "logic": "or", "conditions": [ { "variable": "next_action", "operator": "equals", "operand": "cancel" } ] } },
    { "target_node": "goodbye", "description": "Done", "condition": { "logic": "or", "conditions": [ { "variable": "next_action", "operator": "equals", "operand": "done" } ] } },
    { "target_node": "menu", "description": "Unclear, stay", "condition": { "operator": "always" } }
  ]
}
```

Use extraction for user speech. For API responses use `response_mapping` (tools-and-code.md). It is deterministic and needs no model call.

## End-call nodes

An `end_call` node hangs up. It has a `terminal` object and no outgoing transitions.

```json
{
  "name": "goodbye",
  "node_type": "end_call",
  "on_enter": { "type": "silent" },
  "disable_inactivity_monitor": true,
  "transitions": [],
  "terminal": {
    "type": "function",
    "function": {
      "name": "closing_end",
      "handler": "__function__:end_call",
      "parameters": {
        "type": "object",
        "properties": {
          "message_mode": { "type": "string", "default": "custom" },
          "spoken_message": { "type": "string", "default": "Thank you for calling. Goodbye." }
        }
      }
    }
  }
}
```

| Parameter | Meaning |
|---|---|
| `message_mode` | `custom`: say `spoken_message`. `llm`: the model writes the farewell from `llm_prompt`. `none`: hang up without a farewell |
| `spoken_message` | The fixed farewell for `custom`. `{{var}}` works |
| `llm_prompt` | The instruction for `llm` |
| `interruptible` | `true` opens a short window after the farewell in which the user can still speak. Default: hang up as soon as the agent stops speaking |
| `trigger_timeout` | Length of that window in seconds |
| `trigger_pattern_both` | Farewell phrases, separated by `\|`, that do not cancel the close. Anything else the user says in the window cancels the close and returns the turn to the agent |

Rules:

- **The farewell comes from the terminal, not from `on_enter`.** A node with an `on_enter` line and `message_mode: "none"` hangs up silently. Put the sentence in `spoken_message` and set `on_enter` to `{"type": "silent"}`.
- Set `disable_inactivity_monitor` to `true` and `transitions` to `[]`.
- **The call's `endedReason` is the terminal's `function.name`.** The node name does not affect it. Pick a name that describes the outcome.
- Use several end-call nodes with different farewells and function names when outcomes differ.
- If you set `interruptible`, also set `trigger_pattern_both`. Without a phrase list every polite reply cancels the hang-up. The window is timed on a wall clock and a chat simulation cannot measure it.

Verified in a working builder: `message_mode: "none"` with a silent `on_enter` ends the call when the node is reached. The agent says its goodbye in the previous conversation node.

## Limits

| Limit | Default | Notes |
|---|---|---|
| `max_node_turns` | `10` | Cap on user turns in one node. Only user messages count. Tool results and agent messages do not. There is no "unlimited" value |
| `max_turn_transition` | none | Where to go when the cap is reached. Without it the engine records the overrun and continues with normal routing, so the cap changes nothing |
| `truncation_strategy` | `keep_all` | `keep_all`: full history. `keep_recent`: system message plus the last `truncation_window_size` messages. `summarize`: older messages are replaced by a model-written summary |
| `truncation_window_size` | `10` | Used by `keep_recent` and `summarize` |
| Extraction `min_confidence` | `0.95` | See "Extraction schema" |
| Code `timeout_ms` | `30000` | See tools-and-code.md |

Notes:

- Truncation applies to the dialogue model only. Extraction and routing run before it.
- Give every node that sets `max_node_turns` a `max_turn_transition`. The working builder sets `max_node_turns` to 60 and 80 on its conversation nodes without a `max_turn_transition`. Its calls ended well below those counts, so the behaviour at the cap is not confirmed by it.
- Size the cap from real conversations. A node that handles a whole call can need dozens of user turns.
- The maximum call length in a simulation is set with `maxCallDurationSeconds` (api.md).

## Design rules

- Use `snake_case` node keys that describe the step.
- Keep dialogue in `task_message`, routing in `transitions`, data capture in `extraction_schema`.
- Every path must reach an `end_call` node.
- Put deterministic conditions before `matches_intent` conditions.
- Every passthrough node ends with an `always` transition.
- A transition back to an earlier node is supported.
- Split a step into its own node when it has strict rules of its own or forms a clear state. Keep related optional actions together in one conversation node with several tools.

## Complete example

A clinic assistant. It collects a service and a day, looks up free slots, lets the model book one with a tool, and ends the call.

```json
  "global_nodes": {},

```

What the example shows:

| Node | Feature |
|---|---|
| `collect` | Fixed opening line, extraction with a `date` type, AND group, self-transition, turn cap with a target |
| `find_slots` | Passthrough `api_request` node, baked parameters, node-level `response_mapping`, failure counter, `always` fallback |
| `offer` | A tool the model calls, a model-filled body field, tool-level `response_mapping`, routing on the mapped variable |
| `goodbye_booked`, `goodbye_no_booking` | Two end-call nodes with different `endedReason` values |


# Tools and code

This page describes how a workflow calls HTTP APIs and runs Python. Read [workflow-format.md](workflow-format.md) first.

Statements marked "verified in a working builder" come from a builder that created a 6-node workflow through the REST API. The workflow has code nodes, `api_call` tools, post-hooks and transitions on tool results. Its agent passed its practice cases. Statements marked "seen in a trial call" come from the event log of a simulation call made with that builder.

## Tool function shape

Every external action is a **tool function**. The shape is the same wherever you attach it.

```json
{
  "type": "function",
  "config": { "timeoutMs": 10000, "maxRetries": 2 },
  "function": {
    "name": "lookup_order",
    "handler": "__function__:api_call",
    "description": "Look up one order. CALL it when the caller asks about a specific order.",
    "parameters": {
      "type": "object",
      "properties": {
        "url": { "type": "string", "default": "https://api.example.com/v1/orders/lookup" },
        "method": { "type": "string", "default": "POST" },
        "headers": {
          "type": "object",
          "properties": { "Content-Type": { "type": "string", "default": "application/json" } }
        },
        "body": {
          "type": "object",
          "properties": {
            "customer_id": { "type": "string", "default": "{{customer_id}}" },
            "order_number": { "type": "string", "description": "Order number, digits only", "default": "{{order_number}}" }
          },
          "required": ["order_number"]
        }
      }
    }
  },
  "response_mapping": [
    { "path": "data.status", "variable": "order_status" }
  ]
}
```

| Field | Meaning |
|---|---|
| `type` | Always `"function"` |
| `function.name` | Tool name. The model calls it by this name. Result variables are named after it |
| `function.handler` | Which runtime executes the tool. See the table below |
| `function.description` | Read by the dialogue model when the tool is in `tools`. Ignored in `pre_actions` |
| `function.parameters` | JSON-schema object. `properties` holds the parameters |
| `config.timeoutMs` | Timeout of one attempt, in milliseconds |
| `config.maxRetries` | Tool-level retries of a failed call |
| `config.interruptible` | `false` makes the tool run in the background. See "Background tools" |
| `config.alwaysRunsAt` | Makes the tool a lifecycle tool. See "Lifecycle tools" |
| `response_mapping` | Tool level, for tools in `tools`. Maps the result to variables |
| `pre_process_code` | Python hook that runs before the call |
| `post_process_code` | Python hook that runs after the call |

| Handler | Runs |
|---|---|
| `__function__:api_call` | An HTTP request |
| `__function__:code_exec` | A Python snippet in a sandbox |
| `__function__:end_call` | Hangs up. Used in the `terminal` of an `end_call` node |

Handlers for integrations, knowledge search, call transfer and rescheduling also exist. They are not needed here.

`api_call` parameters:

| Parameter | Meaning |
|---|---|
| `url` | Request URL. `{{var}}` works |
| `method` | HTTP method |
| `headers` | Object. Each header is a property with a `default` |
| `body` | Object. Each body field is a property under `body.properties` |
| `connect_retries` | Transport retries. See "Retries and timeouts" |

## How a parameter gets its value

One key decides, per parameter: `default`.

| Declaration | Who supplies the value | Does the model see the parameter |
|---|---|---|
| `default` with a literal, or with a `{{var}}` that has a value | The workflow. The value is **baked** | No |
| `default` with a `{{var}}` that has no value when the node is entered | The model | Yes, named after the variable, with the property's `type`, `description` and `enum` |
| no `default` | The model | Yes |
| `const` | Nobody. `const` does **not** bake | It only constrains the model's own output |

Rules:

- **Use `default` for fixed backend config** such as `url`, `method` and auth headers. At registration the engine moves every `default` into the tool's base config, resolves `{{var}}` from the variable table, and removes the field from the schema the model sees.
- **Never use `const` for a value you want sent.** The engine reads only `default`. A `{{var}}` inside a `const` never resolves. An `api_call` whose `url` is a `const` fails with "URL is required".
- **Baking happens when the node is entered.** A `{{var}}` default is resolved against the variable table at that moment.

The working builder uses this for every tool: `customer_id` has `"default": "{{customer_id}}"` and is baked from a call variable. Every other body field has `"default": "{{<field name>}}"`, where no variable of that name exists, so the model fills it. Verified in a working builder.

Seen in a trial call: the model's arguments are stored as `<tool>_args.<field>` in the variable table, for example `lookup_order_args.order_number`. They were not stored under the bare field name.

Take care that a model-filled field does not share its name with a variable that is already set when the node is entered. The value would be baked and the model would never see the parameter.

### `api_call` body field rules

- Declare each body field as a leaf under `body.properties.<field>`.
- Put the field's `type`, `description` and `enum` on that leaf. Put required fields in `body.required`.
- Give each leaf its own `default`.
- Do not put a field spec at the top level of `parameters.properties` next to a `body.default` template object. The engine looks for the spec at `body.properties.<field>`, does not find it, and the model sees only "Template variable: name". The `enum` and `description` are lost while the call still works.
- A body that exists only as one `body.default` object also shows as an empty form in the dashboard editor. Saving from there removes the tool.

A `code_exec` tool is different: its parameters are true top-level arguments. Declare a model-filled one as a top-level property without `default`.

### When a baked variable has no value

| Field type | Variable unset | Variable is `""` |
|---|---|---|
| Normal field in an engine-run call (`pre_actions`, lifecycle tool) | The field is dropped from the request. No error | The field is sent empty |
| `code` of `code_exec` | The literal text `{{var}}` stays in the Python source and the snippet crashes | |

Fix: make sure an earlier node always sets the variable, even to a sentinel value. In code, read variables from `vars` and do not splice them in with `{{var}}`.

### Constrain model-filled parameters

When a value must be one of a known set, do not use a free string. The model sometimes invents a value that looks plausible.

- Use an `enum` on the leaf, and list the values in the `description` as well.
- Or use a `number` that is an index into a list, with the valid range in the description. A pre-hook or the backend turns the index into the real value.
- If neither is possible, name the exact source in the description and tell the model to copy the value unchanged.

```json
{
  "type": "object",
  "properties": {
    "queue": {
      "type": "string",
      "description": "Team that takes over. One of: billing, delivery, returns.",
      "enum": ["billing", "delivery", "returns"],
      "default": "{{queue}}"
    }
  },
  "required": ["queue"]
}
```

## `pre_actions` versus `tools`

The placement decides who fires the call.

| Placement | Node type | Who calls it | When |
|---|---|---|---|
| `pre_actions` | `api_request`, `code` | The engine | On node entry, before any model turn |
| `tools` | `conversation` | The dialogue model | During a turn, when the model decides to |
| Workflow-level `tools` with `config.alwaysRunsAt` | none | The engine | At call start or call end |

The platform removes `tools` from non-conversation nodes and `pre_actions` from conversation nodes. It does so without an error: the JSON you sent looks fine, the create call succeeds, and the stored node has an empty array. A node cannot use both.

**Use `pre_actions`** when the call must always run and the model has nothing to decide. Example: after the order number is known, always fetch the order.

**Use `tools`** when the call depends on what the user says. Example: cancel the order only if the caller asks for it.

Differences in behaviour:

| | `pre_actions` | `tools` |
|---|---|---|
| Can be skipped | No | Yes. The model may not call it if the description and the prompt do not push for it |
| Timing | Node entry | Inside a turn. The model can call a tool, speak, then call another |
| Result in the conversation | A tool call and tool result pair is added to the history | The same |
| `response_mapping` lives | On the **node** | On the **tool** |
| `description` | Ignored | The only text the model reads about the tool |

To run a fixed call before a tool-driven conversation, use a passthrough `api_request` node and transition from it into the conversation node. Do not build a long chain of passthrough nodes for optional actions. Put those into one conversation node with several tools.

### A `pre_actions` node

```json
{
  "name": "fetch_order",
  "node_type": "api_request",
  "passthrough": true,
  "passthrough_default_transition": "present",
  "on_enter": { "type": "silent" },
  "pre_actions": [
    {
      "type": "function",
      "config": { "timeoutMs": 10000, "maxRetries": 2 },
      "function": {
        "name": "get_order",
        "handler": "__function__:api_call",
        "description": "Get the order.",
        "parameters": {
          "type": "object",
          "properties": {
            "url": { "type": "string", "default": "https://api.example.com/v1/get_order" },
            "method": { "type": "string", "default": "POST" },
            "headers": { "type": "object", "properties": { "Content-Type": { "type": "string", "default": "application/json" } } },
            "body": { "type": "object", "properties": { "order_number": { "type": "string", "default": "{{order_number}}" } }, "required": [] }
          }
        }
      }
    }
  ],
  "response_mapping": [
    { "path": "data.items", "variable": "items" }
  ],
  "transitions": [
    { "target_node": "present", "description": "always", "condition": { "operator": "always" } }
  ]
}
```

The last `always` transition is mandatory. A passthrough node with no matching transition deadlocks.

### Tool descriptions

In `tools`, the `description` decides whether the model calls the tool.

- Write it as an instruction with the trigger: "CALL it every time the caller gives an order number."
- A plain description such as "Looks up an order" lets the model acknowledge the request in words and never call the tool. That is the most common failure of nodes with many tools.
- If two tools could match, say which one not to use and name the other.
- In `task_message`, put the tool rules before long reference text and state: when a rule says to use a tool, call the tool.
- The working builder also tells the model to call one tool per message and to speak after every tool result. Verified in a working builder. In a trial call a model turn with no text and no tool call produced the error event "The model returned no speakable content".

A tool is available only in the nodes that list it. Seen in a trial call: the model called a tool that the current node did not list. The result was the text "The function `<name>` is not currently available."

## `response_mapping`

`response_mapping` copies values from a call result into named variables. It needs no model call.

```json
{
  "response_mapping": [
    { "path": "data.status", "variable": "order_status" },
    { "path": "data.items", "variable": "items" }
  ]
}
```

| Field | Meaning |
|---|---|
| `path` | Dot path into the tool result |
| `variable` | Name of the variable to set |

### Placement

- For a tool in `tools`: inside the tool object, next to `function` and `config`.
- For `pre_actions`: at the **node level**. A `response_mapping` nested inside a `pre_actions` entry is ignored and the variable never appears.

`extraction_schema` follows the same placement rule if you use it on a call result.

### Where a result lands (trial findings)

Seen in a trial call: the result of an `api_call` is an envelope around the HTTP response.

```json
{
  "status": "success",
  "data": { "ok": true, "verified": true, "attempts_left": 3 },
  "message": "Successfully executed POST request",
  "status_code": 200,
  "header": { "Content-Type": "application/json" }
}
```

`data` is the JSON body the API returned. `header` holds the HTTP response headers.

The engine also writes every result into the variable table by itself, flattened with dots. You do not need a mapping for these. For a tool named `check_answer` whose API returned `{"ok": true, "verified": true, "attempts_left": 3}`, the trial call's variable table held:

| Variable | Value |
|---|---|
| `check_answer_args.<field>` | Each argument the model sent |
| `check_answer_response.status` | `success` |
| `check_answer_response.data.ok` | `true` (a string) |
| `check_answer_response.data.verified` | `true` (a string) |
| `check_answer_response.data.attempts_left` | `3` |
| `check_answer_response.message` | `Successfully executed POST request` |
| `check_answer_response.status_code` | `200` |
| `check_answer_response.header.<Header-Name>` | One variable per response header |
| `check_answer_status_code` | `200` |
| `check_answer_success_count` | Number of successful calls so far |

Each call of the same tool overwrites the previous `_args` and `_response` values.

### Which mapping paths work

- **Start the path at the envelope, with `data.`**. If the API returns `{"ok": true}`, map `data.ok`. If it returns `{"products": [...]}`, map `data.products`. Verified in a working builder, on a tool-level mapping and on a node-level mapping.
- A path without the `data.` prefix (for the same body: `ok`) is not confirmed. A smaller example builder uses it. In an early trial call the mapped variables stayed unset and the transitions on them never fired. The mapping paths of that call are not recorded. The builder that passed uses `data.` paths.
- The flattened key can be used directly as a transition variable: `check_answer_response.data.verified`. Verified in a working builder, which tests the mapped variable and the flattened key in the same OR group as a safeguard.
- Booleans arrive as strings. The trial call showed `true` in lower case in the flattened keys. Test both `"true"` and `"True"`, or map a string field.
- A mapped list or object: the exact form it has later inside `vars` is not confirmed. The working builder reads it defensively. It accepts a list, a JSON string, and flattened keys.

## Routing on tool results

Routing runs again after a tool result arrives. A transition on a result variable fires in the same turn, before any further model turn. Seen in a trial call.

```json
{
  "transitions": [
    {
      "target_node": "load_order",
      "description": "The check passed",
      "condition": {
        "logic": "or",
        "conditions": [
          { "variable": "check_passed", "operator": "equals", "operand": "true" },
          { "variable": "check_passed", "operator": "equals", "operand": "True" },
          { "variable": "check_answer_response.data.verified", "operator": "equals", "operand": "true" },
          { "variable": "check_answer_response.data.verified", "operator": "equals", "operand": "True" }
        ]
      }
    }
  ]
}
```

Rules:

- On a passthrough node, end with an `always` transition so that a failed or empty response does not deadlock.
- Use a tool result to leave a conversation node. The pattern "a closing tool sets a variable, a transition on that variable leads to an `end_call` node" is verified in a working builder.
- To leave a node that carries out an action, do not re-test the user's earlier intent with `matches_intent`. The router looks at the latest user message and can route away before the tool was called. Extract a follow-up enum with a default such as `stay`, and branch with `equals`.

### Success and failure counters

The engine keeps two integer variables per call target. No mapping is needed.

| Placement | Variables |
|---|---|
| `pre_actions` node | `<nodeId>_success_count`, `<nodeId>_failure_count` |
| Tool in `tools` with handler `api_call` | `<toolName>_success_count`, `<toolName>_failure_count` |

Seen in a trial call: `check_answer_success_count` was `2` after two successful calls, and a code node named `setup` produced `setup_success_count` with the value `1`.

```json
{
  "transitions": [
    { "target_node": "give_up", "description": "The lookup failed three times", "condition": { "logic": "or", "conditions": [ { "variable": "lookup_order_failure_count", "operator": "greater_than", "operand": 2 } ] } },
    { "target_node": "ask_again", "description": "always", "condition": { "operator": "always" } }
  ]
}
```

### `suppress_tool_results`

A node-level boolean for nodes that run API calls. With `true` the dialogue model sees only a short `{status: "success"}` summary in place of the raw response. Variables are still mapped and routing still sees them. Use it for large responses, or when the mapped variables already hold everything the model needs.

### Background tools

A tool with `"config": {"interruptible": false}` runs in the background. A user interruption does not cancel it. Its result arrives one or more turns later. The mapped variables, the `_response` keys and the counters are filled as usual, but not in the same turn. A transition that reads them right after the call can find them unset. Gate on the variable with `is_set`.

## Retries and timeouts

| Setting | Where | Default | What it does |
|---|---|---|---|
| `timeoutMs` | `config` | not documented | Time limit of one attempt, in milliseconds |
| `maxRetries` | `config` | not documented | Tool-level retries after a failed response |
| `connect_retries` | `parameters.properties`, as a baked parameter | `2` | Retries when the connection could not be established |
| `timeout_ms` | `code_exec` parameter | `30000` | Time limit of a code snippet |

`connect_retries` in detail:

- It retries only failures to establish the connection: connection refused, or reset during the TCP or TLS handshake. The request never reached the server, so a repeat is safe even for POST.
- HTTP error statuses and timeouts are not retried by it.
- Hard cap `5`. `0` means a single attempt.
- Back-off is 150 ms times the attempt number, with a new connection each time.
- All attempts share one 30 second budget for the request.
- Declare it next to `url` and `method`: `"connect_retries": {"type": "number", "default": 0}`. It is not a `config` field.

The working builder sets `maxRetries` to `0` on tools that write data and to `2` on its read-only `pre_actions` call. A retried write can record the same thing twice if the API is not idempotent.

## Pre and post Python hooks

An `api_call` tool can carry two Python snippets. They run on the server, in a sandbox, right before and right after the call. They are top-level fields of the tool object.

```json
{
  "type": "function",
  "config": { "timeoutMs": 10000, "maxRetries": 0 },
  "function": {
    "name": "check_answer",
    "handler": "__function__:api_call",
    "description": "Check one answer. CALL it every time the caller answers the question.",
    "parameters": {
      "type": "object",
      "properties": {
        "url": { "type": "string", "default": "https://api.example.com/v1/check_answer" },
        "method": { "type": "string", "default": "POST" },
        "body": { "type": "object", "properties": { "answer": { "type": "string", "description": "The caller's answer", "default": "{{answer}}" } }, "required": ["answer"] }
      }
    }
  },
  "pre_process_code": "vars['member_code'] = str(vars.get('member_code') or '').strip().upper()",
  "post_process_code": "try:\n    if isinstance(result, dict):\n        result.pop('header', None)\n        d = result.get('data')\n        if isinstance(d, dict):\n            d['what_to_do_next'] = 'Ask the next question.' if d.get('verified') else 'Ask the same question again.'\nexcept Exception:\n    pass\n"
}
```

| Hook | Names available | Use |
|---|---|---|
| `pre_process_code` | `vars`: mutable dict that fills the `{{var}}` placeholders of the request. `config`: the substituted request with `url`, `method`, `headers`, `body` | Clean a value, or rewrite the whole request |
| `post_process_code` | `result`: the tool result, mutable | Reshape, shorten or extend the result |

Documented behaviour:

- The post-hook runs before `response_mapping` and extraction see the result.
- An empty or whitespace-only string means no hook.
- Hooks are honoured only on `api_call` tools (and on the integration and knowledge search handlers). The platform removes them from any other handler when the workflow is saved.
- In a pre-hook, setting `config['body']` to a string sends that string as the raw body, with no JSON encoding. Set the `Content-Type` header yourself in that case.

### What `result` looks like in a post-hook

The internal reference shows `result` as the response body. A working builder shows otherwise. Verified in a working builder:

- For an `api_call`, `result` is the envelope described above: a dict with `status`, `data`, `message`, `status_code` and `header`. The API's JSON body is `result["data"]`.
- A key that the hook adds inside `result["data"]` reaches the dialogue model as part of the tool result. The working builder adds a `what_to_do_next` sentence there, and its prompt tells the model to obey it.
- `result.pop("header", None)` removes the response headers. The working builder does this on every tool, so that headers do not take up space in the model's context.
- Mapping paths still start with `data.` when a post-hook is present.

The working builder writes every hook inside `try` and `except Exception: pass` and checks types with `isinstance` before use. What the platform does when a hook raises is not documented.

Seen in a test on 10 October: a post-hook can read call variables and write new variables, and a later pre-hook reads them. Not confirmed: whether a change to `result` also changes the flattened `<tool>_response.*` variables.

## Code nodes and `code_exec`

A `code` node runs a Python snippet when it is entered. The snippet is a `code_exec` function in `pre_actions`.

```json
{
  "name": "compute_delivery",
  "node_type": "code",
  "passthrough": true,
  "passthrough_default_transition": "tell_delivery",
  "on_enter": { "type": "silent" },
  "pre_actions": [
    {
      "type": "function",
      "function": {
        "name": "code_exec",
        "handler": "__function__:code_exec",
        "parameters": {
          "type": "object",
          "properties": {
            "code": { "type": "string", "default": "import datetime\ntry:\n    start = datetime.date.fromisoformat(str(vars.get('shipped_on'))[:10])\n    eta = start + datetime.timedelta(days=3)\n    vars['delivery_day'] = eta.isoformat()\n    vars['delivery_state'] = 'known'\nexcept Exception:\n    vars['delivery_day'] = ''\n    vars['delivery_state'] = 'unknown'\n" },
            "timeout_ms": { "type": "number", "default": 10000 }
          }
        }
      }
    }
  ],
  "transitions": [
    { "target_node": "tell_delivery", "description": "always", "condition": { "operator": "always" } }
  ]
}
```

| Parameter | Meaning |
|---|---|
| `code` | The Python source, as a baked `default` string |
| `timeout_ms` | Time limit in milliseconds. Default `30000` |

### Reading and writing variables

- The snippet gets a dict named `vars`. It holds the current workflow variables.
- Read with `vars.get("name")`. A variable that was never set is absent.
- Write with `vars["name"] = value`. Every key the snippet assigns becomes a workflow variable.

Verified in a working builder:

- Call variables are in `vars`. The builder reads `vars.get("now")`, a call variable passed with the simulation.
- The result of an earlier `api_request` node is reachable from `vars` in a later code node. The builder looks for it under the mapped variable name first and under the flattened result keys second. Which of the two held the data is not recorded.
- A string written to `vars["date_facts"]` in a code node resolves as `{{date_facts}}` in the `task_message` of later conversation nodes. Multi-line strings work.
- The standard modules `json`, `re` and `datetime` can be imported.
- The same snippet can run in two code nodes at different points of the call. The later run sees the variables added in between.

### What a code node returns

Seen in a trial call: the result of a successful `code_exec` is

```json
{ "status": "success", "data": null, "message": "Code executed successfully", "status_code": 200 }
```

The snippet's output is not in `data`. Its values reach the workflow only through `vars`. After a code node named `setup` ran, the variable table held:

| Variable | Value |
|---|---|
| each key the snippet wrote, for example `date_facts` | the value, with source `tool_result` and source node `setup` |
| `setup_response.status` | `success` |
| `setup_response.data` | `null` |
| `setup_response.message` | `Code executed successfully` |
| `setup_response.status_code` | `200` |
| `setup_status_code` | `200` |
| `setup_success_count` | `1` |

For a code node the automatic keys are named after the **node**, not after `code_exec`.

### Rules for snippets

- **Do not write `{{` or `}}` in the code.** The internal sources disagree on whether the `code` field is templated. One says it is exempt. Another says placeholders are resolved when the code runs and an unset one is left as literal text, which breaks the Python. The working builder removes every `{{` and `}}` from generated code (a nested dict literal such as `{'a': {'b': 1}}` ends in `}}`) and reads all values from `vars`.
- **Never let a snippet raise.** Wrap the body in `try` and `except`, and write a fallback value for every variable that a later prompt or condition reads. A prompt that references an unset variable shows the literal placeholder to the model.
- **Write strings for routing flags**, such as `known` and `unknown`. Do not route on a Python boolean. See "Do not route on a boolean" in workflow-format.md.
- Keep snippets fast. They block the conversation.
- Do arithmetic, date calculation and counting in code, and give the model the finished facts as text. Verified in a working builder: it computes a block of date facts in a code node and places it in the prompts.
- Treat a code node like an API node: `passthrough: true`, a `passthrough_default_transition`, and a last `always` transition.

### Sandbox limits

| Limit | Value |
|---|---|
| Time | `timeout_ms`, default `30000` |
| Modules | `json`, `re` and `datetime` are verified in a working builder. The full list is not documented |
| Network and file access | Not documented |
| Memory and output size | Not documented |

### `code_exec` as a tool

`code_exec` can also be a tool in the `tools` array of a conversation node, called by the model. Its parameters are top-level arguments, declared without `default` so the model fills them. For such a tool the `code` field resolves `{{var}}` when the tool is called, against the current variable table. The working builder does not use this form, so nothing about it is verified here.

## Lifecycle tools

A tool whose `config.alwaysRunsAt` is a non-empty list is never shown to the model. The engine fires it at a fixed point of the call.

| Value | When |
|---|---|
| `start_of_call` | During call setup, before the first turn |
| `end_of_call` | After the call has ended |
| `each_turn` | Accepted by the schema but not implemented. It never fires |

Put a lifecycle tool that must run on every call into the workflow's top-level `tools` array.

```json
{
  "initial_node": "greeting",
  "nodes": {},
  "tools": [
    {
      "type": "function",
      "config": { "alwaysRunsAt": ["end_of_call"] },
      "function": {
        "name": "push_call_result",
        "handler": "__function__:api_call",
        "parameters": {
          "type": "object",
          "properties": {
            "url": { "type": "string", "default": "https://api.example.com/v1/call-results" },
            "method": { "type": "string", "default": "POST" },
            "body": {
              "type": "object",
              "properties": {
                "summary": { "type": "string", "default": "{{call.analysis.summary}}" },
                "reason": { "type": "string", "default": "{{call.call_end_reason}}" }
              }
            }
          }
        }
      }
    }
  ]
}
```

Rules:

- A workflow-level tool without `alwaysRunsAt` never runs and the model never sees it.
- A lifecycle tool in a node's `tools` runs for `start_of_call` only on the `initial_node`, and for `end_of_call` only on the node in which the call ended.
- If a `{{var}}` parameter is still unresolved, one model call fills the parameters. If everything resolves, the handler runs directly.
- `response_mapping` is applied for `start_of_call`. It is not applied for `end_of_call`.
- At the end of a call the order is: call analysis, then `end_of_call` tools, then success-criteria judging. An `end_of_call` tool can use `{{call.analysis.summary}}`, `{{call.analysis.structured_data_str}}`, `{{call.call_end_reason}}`, `{{call.call_end_reason_category}}`, `{{call.call_tags}}` and `{{call.duration}}`.
- A malformed lifecycle tool is dropped at run time without an error. Validate with a dry run (api.md).

## Tool results and the next turn

After a tool call returns, the model sees the result and has to produce the next turn itself. Two things were seen in practice runs with the hackathon's agent model:

- **The agent says nothing after the tool call.** The result arrives, no assistant message follows, and the simulated customer hangs up after waiting. It happens more often when the result is bare data such as `{"ok": true, "verified": true}`.
- **The agent ignores a negative result.** For example it reads `"verified": false` and moves on to the next question as if the answer had passed.

What fixed both in a working builder (verified, see the post-hook section above): a post-hook on the tool that adds one plain instruction line to the result before the model sees it, for example a `what_to_do_next` field that says what the answer means and what to say or call next. The model then has something to act on.

Also say it in the step's prompt: after every tool result, speak to the customer or call the next tool. Never end a turn with nothing.

## Checklist

- Fixed values use `default`, never `const`.
- Each `api_call` body field is a leaf under `body.properties` with its own `default`, `description` and `enum`.
- `tools` only on `conversation` nodes. `pre_actions` only on `api_request` and `code` nodes.
- `response_mapping` on the tool for `tools`, on the node for `pre_actions`.
- Mapping paths start with `data.`.
- Booleans from results are tested as `"true"` and `"True"`, or replaced by string fields.
- Every passthrough node ends with an `always` transition.
- Code reads and writes through `vars`, never raises, and contains no `{{` or `}}`.
- Tool descriptions say when to call the tool.
